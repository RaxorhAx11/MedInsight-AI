# Database Documentation

MedInsight AI uses **MongoDB** accessed via **Mongoose 6**. The database is configured entirely through the `MONGODB_URI` environment variable, supporting both local MongoDB and MongoDB Atlas.

---

## Connection Configuration

File: `server/db.js`

| Setting | Default | Environment Variable |
|---|---|---|
| Connection URI | — | `MONGODB_URI` (required) |
| Max Connection Pool Size | 10 | `MONGODB_MAX_POOL_SIZE` |
| Server Selection Timeout | 5000 ms | `MONGODB_SERVER_SELECTION_TIMEOUT_MS` |
| Socket Timeout | 45000 ms | `MONGODB_SOCKET_TIMEOUT_MS` |
| Auto Index | `true` in dev, configurable | `MONGODB_AUTO_INDEX` |
| Retry Attempts | 5 | `MONGODB_RETRY_ATTEMPTS` |
| Retry Delay | 5000 ms | `MONGODB_RETRY_DELAY_MS` |

The connection module implements exponential-wait retry logic. If the maximum retry attempts are reached without success, the process exits with code 1.

## Collections

### `users`

Stores user account information.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Auto | MongoDB document ID |
| `firstName` | String | Yes | User's first name |
| `lastName` | String | Yes | User's last name |
| `email` | String | Yes | Unique, lowercase, trimmed |
| `password` | String | Yes | bcrypt hash |
| `age` | Number | Yes | User's age |
| `height` | String | Yes | e.g. "165cm" |
| `weight` | String | Yes | e.g. "60kg" |
| `sex` | String | Yes | Enum: `Male`, `Female`, `Other` |
| `settings.theme` | String | No | `light` (default) or `dark` |
| `settings.emailAlerts` | Boolean | No | Default: `true` |
| `settings.aiInsights` | Boolean | No | Default: `true` |
| `settings.autoAnomaly` | Boolean | No | Default: `true` |
| `avatar` | String | No | URL to profile avatar (Cloudinary or local) |

**Indexes:** MongoDB default `_id` index + unique index on `email` (defined via `unique: true` in schema).

---

### `files`

Stores metadata for every uploaded PDF report.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Auto | MongoDB document ID |
| `userId` | ObjectId (ref: `user`) | Yes | Owner user |
| `fileName` | String | Yes | Original file name |
| `filePath` | String | Yes | Cloudinary URL or local relative path |
| `publicId` | String | No | Cloudinary public ID (null for local storage) |
| `mimetype` | String | No | `application/pdf` |
| `uploadDate` | Date | No | Default: `Date.now` |
| `description` | String | No | Optional user description |
| `testDate` | Date | No | Date of the medical test; defaults to `Date.now` |

**Indexes:**
- `{ userId: 1, testDate: -1 }`
- `{ userId: 1, uploadDate: -1 }`

---

### `bloodreports`, `urinereports`, `stoolreports`, `semenanalyses`, `papsmears`, `swabtests`

All 6 report collections share the same schema structure (defined by `createGenericReportSchema()` in `models/genericReportSchema.js`).

**Report document fields:**

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Auto | MongoDB document ID |
| `userId` | ObjectId (ref: `user`) | Yes | Owner user |
| `reportDate` | Date | Yes | Date of the lab test |
| `description` | String | No | Optional notes |
| `fileId` | ObjectId (ref: `File`) | No | Link to the source uploaded file |
| `biomarkers` | Array | Yes | Array of biomarker subdocuments |

**Biomarker subdocument:**

| Field | Type | Required | Description |
|---|---|---|---|
| `name` | String | Yes | Biomarker name (e.g. "Hemoglobin") |
| `description` | String | Yes | Human-readable description |
| `result` | Mixed | Yes | Numeric or string result value |
| `unit` | String | No | Measurement unit (e.g. "g/dL") |
| `referenceRange.min` | Mixed | No | Minimum normal value |
| `referenceRange.max` | Mixed | No | Maximum normal value |
| `status` | String | No | `Normal`, `High`, `Low`, `Not Mentioned` |

**Indexes (on each collection):**
- `{ userId: 1, reportDate: -1 }`
- `{ userId: 1, fileId: 1 }`

### `conversations`

Stores AI chat conversation history.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Auto | MongoDB document ID |
| `userId` | ObjectId (ref: `user`) | Yes | Owner user |
| `conversationID` | String | Yes | UUID string generated by the frontend |
| `topic` | String | No | Optional conversation topic label |
| `messages` | Array | No | Array of message subdocuments |

**Message subdocument:**

| Field | Type | Required | Description |
|---|---|---|---|
| `sender` | String | Yes | `user` or `bot` |
| `message` | String | Yes | Message text |
| `timestamp` | Date | Yes | Default: `Date.now` |

**Indexes:**
- `{ userId: 1, conversationID: 1 }` — unique

### `reportchunks`

Stores text chunks and their 768-dimension vector embeddings generated from uploaded PDF reports for semantic vector retrieval.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Auto | MongoDB document ID |
| `userId` | ObjectId (ref: `user`) | Yes | Owner user |
| `reportId` | ObjectId (ref: `File`) | Yes | References the uploaded File ID (corresponds to reportId) |
| `chunkText` | String | Yes | Plain text snippet representing the panel/notes |
| `chunkType` | String | Yes | Type of chunk (e.g. `biomarker_group` or `doctor_notes`) |
| `embedding` | Array (Number) | Yes | 768-dimension vector embedding (validates exactly 768 length) |
| `createdAt` | Date | No | Default: `Date.now` |

**Indexes:**
- `{ userId: 1, reportId: 1 }`
- `{ reportId: 1 }`
- `reportchunks` (MongoDB Atlas Search index of type `vectorSearch` on the `embedding` path)

---

### `activities`

Stores chronological user activity log entries.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Auto | MongoDB document ID |
| `userId` | ObjectId (ref: `user`) | Yes | Owner user |
| `activityType` | String | Yes | Enum: `upload`, `analysis`, `alert`, `delete`, `profile`, `settings` |
| `title` | String | Yes | Short activity title |
| `description` | String | Yes | Detailed description |
| `status` | String | No | Enum: `Completed`, `Processing`, `Failed`, `Warning`. Default: `Completed` |
| `createdAt` | Date | No | Default: `Date.now` |

**Indexes:**
- `{ userId: 1, createdAt: -1 }`

---

### `notifications`

Stores in-app notification records.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Auto | MongoDB document ID |
| `userId` | ObjectId (ref: `user`) | Yes | Owner user |
| `type` | String | No | Enum: `info`, `success`, `warning`, `danger`. Default: `info` |
| `message` | String | Yes | Notification text |
| `read` | Boolean | No | Default: `false` |
| `link` | String | No | Optional frontend route to navigate to |
| `createdAt` | Date | No | Default: `Date.now` |

**Indexes:**
- `{ userId: 1, createdAt: -1 }`

## Data Relationships

```
users (1)
  ├── files (N)              — userId ref
  ├── bloodreports (N)       — userId ref, optional fileId ref → files
  ├── urinereports (N)       — userId ref, optional fileId ref → files
  ├── stoolreports (N)       — userId ref, optional fileId ref → files
  ├── semenanalyses (N)      — userId ref, optional fileId ref → files
  ├── papsmears (N)          — userId ref, optional fileId ref → files
  ├── swabtests (N)          — userId ref, optional fileId ref → files
  ├── reportchunks (N)       — userId ref, reportId ref → files
  ├── conversations (N)      — userId ref
  ├── activities (N)         — userId ref
  └── notifications (N)      — userId ref
```

All `userId` fields reference the `users` collection. The `fileId` on report documents references the `files` collection and links the parsed biomarker data back to its source PDF.

---

## Biomarker Reference Data

File: `server/data/biomarkers.json`

This JSON file contains the reference database for all supported biomarkers. Each entry contains:

- `description` — human-readable description
- `aliases` — alternative names used for PDF regex matching
- `unit` — measurement unit
- `referenceRange.min` — minimum normal value (numeric or qualitative string)
- `referenceRange.max` — maximum normal value (numeric or qualitative string)

This file is loaded into memory at server startup and used by both the PDF extraction pipeline and the API endpoints.

## Data Flow Summary

```
1. User uploads PDF
   → biomarkers.json lookup → extract biomarkers → save to files collection
   → split report text into panels and doctor notes → generate 768-dim embeddings → save to reportchunks

2. User saves report
   → save to report collection (bloodreports, urinereports, etc.)
   → link to files via fileId
   → create entries in notifications and activities

3. User views biomarkers
   → query report collection for userId, sort by reportDate
   → merge with biomarkers.json for expected biomarker list

4. User opens AI chat
   → generate embedding for user's question
   → query reportchunks collection using $vectorSearch filtered by userId & reportId (with chronological fallback)
   → format retrieved chunks as context system instruction
   → save messages to conversations collection

5. User deletes a file
   → delete from files collection
   → delete all matching documents from all 6 report collections
   → delete associated report chunks from reportchunks collection
```

## Recommended Indexes for Production

The following indexes are defined in the Mongoose schemas and should be created automatically (or manually in Atlas):

```javascript
// files
{ userId: 1, testDate: -1 }
{ userId: 1, uploadDate: -1 }

// all report collections
{ userId: 1, reportDate: -1 }
{ userId: 1, fileId: 1 }

// reportchunks
{ userId: 1, reportId: 1 }
{ reportId: 1 }

// conversations
{ userId: 1, conversationID: 1 }  // unique

// activities
{ userId: 1, createdAt: -1 }

// notifications
{ userId: 1, createdAt: -1 }
```

> **Note:** In production, set `MONGODB_AUTO_INDEX=false` and manage index creation through MongoDB Atlas or migration scripts to avoid performance overhead at startup. Additionally, ensure the Atlas Search Vector index named `reportchunks` is configured on the `reportchunks` collection.
